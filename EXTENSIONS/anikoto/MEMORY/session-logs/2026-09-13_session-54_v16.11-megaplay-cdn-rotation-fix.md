**Root cause:** megaplay's default CDN serves the master m3u8 only to
browser-like TLS clients. The v16.10 flow called getSourcesNew WITHOUT the
`s=` CDN selector (it even dropped HD-1's `?s=tcdn` from the iframe URL), so
every stream resolved to an unfetchable master → all hosters null → "broke".

The site's own player (lib/newclient.min.js) appends the page's `s=` query
param to every getSources XHR/fetch (`w(u)` rewrite) — HD-1 ships `?s=tcdn`.
SegmentStrip: hosts matching
`/ibyteimg\.com|tiktokcdn\.com|ipstatp\.com|yoot\.akirax\.buzz/i` have the
first **252 bytes** stripped by the player (PNG disguise; our proxy's
`stripPngHeader` already handles this — IEND + 0x47 scan).

## Fix (AnikotoExtractors.kt, commit `c1ed16a`, tag `v16.11`)
- `fetchSourcesData(host, dataId, audioType, sParam)`: iterate s-candidates
  **[iframe's own s, "tcdn", ""]** × **[getSourcesNew, getSources]**; accept the
  first combo whose **master m3u8 VERIFIES as fetchable** (starts with #EXTM3U).
- New `fetchAndVerifySources()` helper; master text returned pre-fetched inside
  `SourcesData(masterM3u8, tracks, masterText)` so resolveVidTube doesn't re-fetch.
- **WebView (Chrome TLS) last resort** for the master only (after OkHttp fails) —
  mirrors session 30-31 pattern without touching the hot path.
- `resolveVidTube` extracts `s` from the iframe URL query (HD-1 → "tcdn").
- Self-correcting against future CDN rotation — no hardcoded m3u8 hosts.
- `extVersionCode = 11` (v16.11); extVersionId stays 11 (source id stable).
